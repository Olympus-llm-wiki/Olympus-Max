# Разработка Olympus с ECC

Навык [olympus-development](../.agents/skills/olympus-development/SKILL.md) связывает
существующую карту проектов и workspace Olympus с выбранными навыками ECC.
Код и требования остаются в целевом проекте. Рабочее состояние сохраняется в
Olympus; ECC Memory Vault не становится второй базой задач.

Обычный запрос: «Продолжи разработку проекта …». Явный вызов:
`$olympus-development Продолжи работу по актуальному checkpoint проекта …`.

## Результат первого этапа

Добавлены короткий адаптер и проверка свежести результатов перед `finish`.
Существующие навыки Matt Pocock, OpenSpec, Serena и настройки ECC сохранены.
Адаптер выбирает одну процедуру для этапа; он не скрывает остальные навыки из
каталога и не запускает ненативные Claude slash-команды.

Перед работой используется [маршрут проектов](project-workspaces.md). Для внешнего
проекта сохраняется его собственный трекер; OpenSpec Olympus описывает изменения
самого Olympus. Рабочая копия не перенастраивает существующие MCP.

## Квитанции проверок

Помощник [checkpoint_guard.py](../.agents/skills/olympus-development/scripts/checkpoint_guard.py)
исполняет явно переданную команду без shell. До и после неё он снимает существующий
ограниченный workspace-контекст: привязки, Git, учитываемые изменённые файлы,
выбранные пути и инструкции. Код вывода, argv, cwd, HEAD и digest контекста сохраняются
в новой квитанции. Вывод команды идёт в stderr, в квитанцию не копируется.

Квитанции размещаются **вне каталогов выбранных ресурсов** — например, в отдельной
папке доказательств работы под пользовательским state Olympus. Файл не перезаписывается.
Все команды запускаются после проверки доступности фактов/инструкций и в ранее
разрешённой области. Помощник не извлекает команды из памяти и не даёт новых прав.

Из корня Olympus, заменив обозначенные пути/ID фактическими значениями:

```bash
python3 .agents/skills/olympus-development/scripts/checkpoint_guard.py \
  check <work-id> --cwd /absolute/project \
  --output /absolute/evidence/check-01.json --timeout 120 \
  -- python3 -m unittest discover -s tests -v
```

Для второго теста/lint/build создаётся отдельная квитанция на том же workspace version
и контексте. При неуспешной команде, изменении файлов во время проверки, истечении
таймаута либо ошибке запуска эта квитанция не допускает завершение.

После проверок подготовь JSON с непустыми `done`, `artifacts`, пустым `pending`,
`next_step` и остальными нужными полями workspace. Поле `checks` помощник заполнит
из выбранных квитанций:

```bash
python3 .agents/skills/olympus-development/scripts/checkpoint_guard.py \
  finish <work-id> --update /absolute/evidence/finish.json \
  --receipt /absolute/evidence/check-01.json \
  --receipt /absolute/evidence/check-02.json
```

Обычный `--state` Olympus поддерживается перед `check/finish`. Пилот всегда передаёт
выделенный state; рабочий state по умолчанию — `OLYMPUS_STATE_DIR` либо
`~/.local/state/olympus`. Помощник вычисляет корень своего checkout, поэтому работает
и в отдельном worktree через `python3`, без копирования venv и изменения MCP.

## Изменения после проверки

Новый код, изменённые инструкции, HEAD или checkpoint делают старые квитанции
непригодными. Сначала перечитай workspace и обнови область при необходимости,
затем выполни необходимые проверки заново. Коммиты следуют договору проекта;
если коммит меняет HEAD после проверки, получи новую квитанцию перед finish.
Чужой файл не откатывается ради совпадения digest.

Результат `finish` записывается штатным workspace API с проверкой ожидаемой версии.
Исторические результаты сохраняются в прежних версиях; в текущую запись попадают
выбранные свежие checks. Помощник не запускает retain, не меняет trust, не создаёт
внешние задачи и не копирует данные в ECC vault.

`finish` отклоняет `selection` и `intent` в итоговом JSON: область меняется отдельным
checkpoint, после которого нужны новые проверки. Если снимок после команды стал
недоступен, сохраняется полноценная неуспешная квитанция с результатом команды.

## Границы доказательства

Это защита от случайного применения устаревшего результата, не независимая
аттестация агента: локальный владелец файлов способен подделать JSON. Достаточность
тестов и ревью против постановки оцениваются отдельно. Команда сама определяет свои
побочные эффекты; запуск `check` не является sandbox.

Снимок ограничен действующим контрактом workspace. Игнорируемые Git артефакты,
внешние сервисы, окружение зависимостей и содержимое credential-файлов не получают
полного доказательства неизменности. Файловой блокировки между проверкой и записью
нет: параллельную разработку изолируют worktree/владением путями.

Штатный `olympus workspace finish` сохраняет прежнее поведение. Дополнительная
сверка применяется при использовании этого адаптера; обход помощника не объявляется
проверенным ECC-маршрутом. Недоступность Hindsight не мешает локальной навигации и
checkpoint, но доставка/поиск по модели и удалённые копии требуют отдельных проверок.

## Проверка и откат

```bash
PYTHONPATH=src python3 -m unittest discover -s tests -p test_development_guard.py -v
python3 scripts/ecc-development-pilot.py --output /absolute/new-pilot-directory
bash scripts/devtools-openspec.sh validate integrate-ecc-development --strict
```

Пилот создаёт отдельные Git-репозитории и Store, делает небольшую функцию и исправление,
проверяет RED/GREEN, продолжение новым процессом, отказ на устаревшие проверки и
сохранность чужой работы. Это испытание маршрута, а не оценка каждого навыка ECC.

При откате убирается маршрут к этому навыку и его собственные файлы. Проектные
данные, код, требования и записи Olympus сохраняются. Переключение/удаление Matt
и массовое включение ECC observers не входят в этот этап.

Квитанция первого этапа: [проверки и границы](evidence/ecc-development.json).
