# Работа над проектами из Olympus

Владелец называет проект и цель в задаче Olympus. Агент находит ресурсы, читает нужные инструкции, выполняет действия с явным рабочим каталогом и возвращает результат сюда. Код и документация проекта остаются на своих местах; их формат менять для подключения не требуется.

## Порядок работы агента

1. При запросе о проекте вызови `project show <имя>`. Если проект неизвестен, проверь `project list`, доступный native список проектов Codex и названные владельцем источники. Добавляй только нужный проект; найденные старые копии не активируй автоматически. При нескольких обоснованных кандидатах спроси конкретный недостающий выбор.
2. Для продолжения вызови `workspace resume --project <id>` или укажи точный work ID из `workspace list`. При нескольких работах выбери по задаче владельца. Прочитай возвращённые изменения, текущие инструкции и постановку по ссылкам; сохранённое резюме само по себе не является новым разрешением.
3. Для новой работы вызови `workspace prepare`, явно выбрав ресурсы и пути. `ready` означает успешную локальную проверку перечисленного контекста; это не разрешение на изменения и не проверка приложения. Прочитай указанные инструкции. После этого создай рабочую запись через `workspace start` с текущим ID задачи Codex, если он доступен.
4. Выполняй работу штатными инструментами с явным `workdir`/`git -C` целевого репозитория. При изменении области сначала обнови контекст и прочитай вложенные инструкции. Учитывай чужие изменения и пересечения работ. Рабочую копию и исходную Git-точку выбирай по задаче; сама карта их не переключает. Сервер требует обычной проверки портов и именованной tmux-сессии.
5. На содержательной границе сохраняй `workspace checkpoint`: сделанное, оставшееся, проверки и следующий шаг. Команда обновляет снимок контекста, но не доказывает, что инструкции прочитаны. Перед завершением укажи реальные результаты и артефакты; `workspace finish` отклонит незавершённую работу или непрошедшие проверки. Итог возвращай в текущую задачу Olympus.

Карта и рабочие записи читаются без модели/сети и без секретной обёртки. Общий поиск памяти остаётся отдельной командой с прежним охватом. Документы AOS и сохранённые снимки — материалы, а старые инструкции для моделей не становятся действующими из-за поля `active` в документе.

## Команды

Запускай CLI из репозитория Olympus либо через абсолютный путь к его `python3 ops.py`.

```bash
python3 ops.py project list
python3 ops.py project show Marketly
python3 ops.py project check marketly
python3 ops.py workspace list --project marketly
python3 ops.py workspace resume --project marketly
```

`prepare/start` принимают `--project`, `--goal`, повторяемый `--resource` и `--path resource-id:relative/path`. По умолчанию выбираются активные ресурсы для чтения. Для `--intent edit` обязательно явно назвать пути. Начало записи также принимает work ID, `--thread-id` и повторяемый `--reference` на постановку/источник. Имена ресурсов сначала прочитай из карты, не копируй выдуманное имя из примера.

`checkpoint/finish` принимают work ID, путь к JSON и `--expected <version_id>` последней прочитанной записи. Массивы заменяются целиком; прежняя редакция доступна через `workspace show <id> --version <old-version>`. При конфликте перечитай запись вместо перезаписи. Для расширения области передай `selection` и `intent` в checkpoint.

Минимальное содержательное обновление:

```json
{
  "done": ["Что выполнено"],
  "pending": ["Что осталось"],
  "next_step": "Конкретный следующий шаг"
}
```

Дополнительные поля: `references`, `artifacts`, `commits`, `limitations`, `thread_id`, `status`. Проверка в `checks` содержит `argv`, абсолютный `cwd`, `exit_code` (null для непроверенного), `checked_at`, `git_head` (null вне Git) и `note`. Это зарегистрированное наблюдение агента, а не автоматический запуск или независимая аттестация. Для завершения нужны непустые `done`, `artifacts`, `checks`, пустой `pending`, успешные checks и пригодный текущий контекст. Исторические неудачные проверки сохраняются в прежних версиях.

## Подключение проекта

`project register /absolute/map.json --expected new` сохраняет первую редакцию; обновление требует прежний version ID. JSON имеет поля `schema: 1`, ASCII `id`, `name`, `aliases`, `requirements` (ссылки на место постановок) и `resources`.

Каждый ресурс содержит `id`, `role` (`code`, `knowledge`, `design`, `reference`), `purpose`, `status` (`candidate`, `active`, `retired`), ровно один из `path`/`url` и `provenance` с `source`, `checked_at`, `basis`. Для активного локального ресурса регистрация сама снимает физическую/Git-привязку. Входное поле `binding` не принимается за доказательство и вычисляется заново. Историческое «canon» не является основанием актуальности. У `code` должен быть локальный Git-каталог.

`actions` — необязательные описания команд: `name`, массив `argv`, ссылка `source`. Они не исполняются и возвращаются как `not_executed`. Дополнительные файлы инструкций можно явно указать в `instructions`; для кода автоматически перечисляются AGENTS.override.md/AGENTS.md от Git-корня до выбранных путей. Произвольные `config.toml`, hooks, skills и MCP таким чтением не активируются. Глобальные и пользовательские инструкции текущей сессии сохраняют приоритет. Для нестандартных имён инструкций указывай явные пути.

Личные карты и записи находятся в существующем локальном Store вне Git, как архивные версии и settings-указатели `routing.*`. Нет отдельной очереди исполнения, активного проекта на всю машину или автоматического retain. Текущий указатель меняется после сохранения версии под блокировкой Store с проверкой предыдущей версии. Незавершённое сохранение не продвигается автоматически при recovery.

## Границы и проверка

Serena и OpenSpec-обёртка Olympus привязаны к Olympus. Для другого репозитория используй его доступный CLI или обычный shell, не перенастраивая эти инструменты. Смена cwd не меняет права, доверие, MCP или основной репозиторий интерфейса Codex. Прикрепление дополнительных папок к native проекту — необязательное удобство; внутренние базы приложения для этого не редактируются.

Снимок показывает Git HEAD, ветку, локальные изменения, hashes выбранных файлов и инструкций. Это не файловая блокировка; внешние процессы могут продолжить работу. Credentials не читаются как ресурсы, для изменённых `.env*` сохраняются только файловые metadata. Поиск кандидатов не обходит весь диск. URL только перечисляются, их доступность и содержание требуют отдельного чтения.

После локального restore карта и история доступны, но барьер восстановления виден в контексте и не снимается автоматически. Удалённая копия и готовность Hindsight проверяются отдельными квитанциями.

```bash
PYTHONPATH=src .venv/bin/python -m unittest discover -s tests -p test_workspaces.py -v
.venv/bin/python scripts/project-workspaces-pilot.py --output /absolute/new-pilot-directory
```

Пилот создаёт два временных репозитория, реально изменяет и проверяет один, сохраняет checkpoint и продолжает из нового CLI-процесса. Он проверяет сохранность чужого файла и второго репозитория. Пилот не создаёт пользовательскую задачу Codex: проверка следующей новой задачи Olympus учитывается отдельно.
